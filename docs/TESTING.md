- 전이 규칙, 되돌리기·취소 복원 방향 제한, `stale` 처리, 오래된 되돌리기 거절
- 익명: 원본 테이블 조회·RPC·공개 테이블 직접 쓰기 모두 거부
- 로그인했지만 명단에 없는 계정·비활성 계정: RPC 거부, 원본 조회 0건
- 직원도 테이블 직접 UPDATE 불가 (RPC 만)
- 공개 상태 컬럼에 메뉴·메모·직원·취소 사유 없음

## 부하 시험 시나리오

> 운영 프로젝트가 아닌 **시험용 Supabase 프로젝트**에서 진행합니다. 동시 연결 수(WebSocket)와 초당 HTTP 요청 수는 다른 지표입니다.

준비: 시험 프로젝트에 마이그레이션 적용 → 직원 계정 1개 등록 → 회차 시작 → `.env.test` 에 URL·키.

```bash
CLIENTS=100 ROUNDS=3 STAFF_EMAIL=… STAFF_PASSWORD=… node --env-file=.env.test scripts/realtime-load.mjs
```

1. **동시 연결**: 손님 100 + 직원 2 기준. 스크립트가 100개 Realtime 연결을 열고 구독 성공/실패 수를 기록
2. **상태 반영**: 조리 완료·수령 완료 각각에 대해 100개 연결의 수신률과 지연 p50/p95/최대 (목표 p95 < 2000ms)
3. **재접속 폭주**: 연결 유지 중 직원 화면에서 상태 변경을 계속하며, 별도로 손님 탭 수십 개를 새로고침 → 초기 스냅샷 HTTP 요청 수(손님 1명당 3~4회: 회차·수령 가능·최근 완료·내 번호)와 오류율 확인
4. **보조 조회**: Realtime 이 끊기면 손님 1명당 10~15초에 약 3~4회 요청 → 100명 기준 평균 초당 약 20~40 요청. 이 상태를 5분 유지해 오류율 확인
5. 기록: 연결 실패율, 이벤트 수신률, 지연, Supabase 대시보드의 Realtime 메시지 수·동시 연결 수·API 오류 로그

메시지 사용량 추정: 상태 변경 1회 = 구독자 수만큼 메시지 (100명 → 약 100건). 주문 500건 × 변경 2~3회 × 100명 ≈ 10~15만 건/일.
플랜의 Realtime 한도(동시 연결·초당 메시지·월 메시지)는 공식 문서에서 다시 확인하세요.
