DB 테스트로 확인한 항목

- 열린 회차 1개 제약, 미처리 주문이 있으면 종료 차단, 종료된 회차 수정 불가·기록 보존
- 새 회차에서 같은 번호 재사용 가능, 손님은 현재 회차 공개 상태만 조회
- 중복 번호 거절(취소·수령 완료 번호 포함) + 기존 주문 반환, 잘못된 메뉴·수량은 전체 롤백
- 같은 `request_id` 재시도 → 한 번만 생성/반영
- 전이 규칙, 되돌리기·취소 복원 방향 제한, `stale` 처리, 오래된 되돌리기 거절
- 익명: 원본 테이블 조회·RPC·공개 테이블 직접 쓰기 모두 거부
- 로그인했지만 명단에 없는 계정·비활성 계정: RPC 거부, 원본 조회 0건
- 직원도 테이블 직접 UPDATE 불가 (RPC 만)
- 공개 상태 컬럼에 메뉴·메모·직원·취소 사유 없음
- `public_board`: 익명 호출 가능, 회차·목록·내 번호를 한 번에 반환, 메모 미포함, 종료된 회차는 빈 목록

## 부하 시험 시나리오

> 운영 프로젝트가 아닌 **시험용 Supabase 프로젝트**에서 진행합니다. 동시 연결 수(WebSocket)와 초당 HTTP 요청 수는 다른 지표입니다.

준비: 시험 프로젝트에 마이그레이션 적용 → 직원 계정 1개 등록 → 회차 시작 → `.env.test` 에 URL·키.

```bash
CLIENTS=100 STAFF_EMAIL=… STAFF_PASSWORD=… node --env-file=.env.local scripts/realtime-load.mjs
```

스크립트는 실제 앱 구조를 그대로 흉내 냅니다: 손님 N명이 각자 자기 번호만 구독하고 10~15초마다 `public_board` 를 조회하는 동안, 시험 주문 N개를 0.2초 간격으로 조리 완료 처리해 각 손님이 받기까지의 지연을 잽니다. 끝나면 시험 주문은 ‘부하 시험’ 사유로 취소됩니다.

기록할 것: 연결 실패율, 이벤트 수신률, 지연 p50/p95/최대, 주기 조회 오류, Supabase 대시보드의 Realtime 메시지·동시 연결·API 오류.

메시지 사용량 추정: 손님은 자기 번호만 구독하므로 상태 변경 1회 ≈ 메시지 1~2건 (직원 기기 포함). 주문 500건 × 변경 3회 × (손님 1 + 직원 2) ≈ 4,500건/일. 주기 조회는 100명 기준 초당 약 8회(HTTP).
플랜의 Realtime 한도(동시 연결·초당 메시지·월 메시지)는 공식 문서에서 다시 확인하세요.
